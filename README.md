# 心桥 · 城市社区心理咨询预约与危机转介平台

面向城市社区的心理服务一体化平台：居民在线预约 → 平台按**咨询师资质 / 可用时段 / 主题匹配 / 危机等级**智能生成预约 → 社工咨询前初筛 → 咨询师记录与转介 → 随访 / 回执 / 评价归档；**预约筛查、咨询记录、危机处置严格分权管理**，危机个案与普通咨询分流，并向社区管理者汇总服务量、风险等级与转介结果，辅助“是否增加咨询师 / 社工培训 / 深化医院合作”的供给决策。

技术栈：**React 18 + TypeScript + Ant Design（Vite 构建）/ NestJS 10 + TypeORM / PostgreSQL 16**，Docker Compose 一键部署（nginx 非 root 托管前端并反代后端）。

---

## 原始需求

> 建设城市社区心理咨询预约与危机转介平台，可采用 React、NestJS 和 PostgreSQL。居民预约时填写咨询主题、年龄、紧急程度、是否有自伤风险、既往咨询、可约时间和保密授权。平台根据咨询师资质、可用时段、主题匹配和危机等级生成预约。咨询前，社工完成初筛，确认是否适合社区咨询、是否需要家属参与或是否直接转介医院。咨询过程中，咨询师记录主题、风险评估、干预建议和下次计划；记录需要按权限保护。若来访者爽约、风险升级、家属要求查看记录、咨询师请假或需要转介精神专科，平台要把预约、保密、危机评估、转介和随访串到同一服务链。咨询结束后，随访、转介回执、危机事件和服务评价进入档案，社区可评估服务供给和风险响应。平台还要把咨询服务量、风险等级和转介结果汇总给社区管理者，帮助判断是否增加咨询师、社工培训或医院合作。转介结果会影响社区服务供给。平台还要把预约筛查、咨询记录和危机处置严格分权管理，社区既能追踪服务效果，也能保护来访隐私，避免危机事件和普通咨询混在一起。

## 一、快速启动（Docker 一键部署）

要求：已安装 Docker 与 Docker Compose 插件。

```bash
cd /workspace
cp .env.example .env          # 可按需修改宿主机发布端口 CC_PUBLISH_PORT
docker compose up -d --build  # 构建并启动 db / app(NestJS) / web(nginx+React)
```

- 仅 **web 服务**把端口发布到宿主：`${CC_PUBLISH_PORT}:8080`（默认 `3045`）。
- PostgreSQL 与 NestJS 后端**不发布宿主端口**，仅在 compose 内网通过服务名 `db` / `app` 互访。
- 验证实际映射端口：`docker compose port web 8080`，然后浏览器访问 `http://host.docker.internal:<端口>/`。
- 健康检查：`http://host.docker.internal:<端口>/api/health`（容器内含 HEALTHCHECK，启动时自动等待数据库就绪并写入演示种子数据）。
- 停止与清理：`docker compose down`（加 `-v` 同时删除数据卷）。

> 本工程的 compose 项目名由环境变量 `COMPOSE_PROJECT_NAME` 固定，无需也不要手动指定 `-p`。

## 四、高危预约即时分流

居民提交预约时，平台对「咨询主题/既往咨询」文本做自伤风险关键词识别（自杀、轻生、不想活、割腕、吞药、遗书等 30+ 词）：

- **命中关键词即跳过普通排班**：申请状态置为 `高危分流中`，不生成预约、匹配接口对居民/社工均关闭（403），即使居民把紧急程度选为“普通”也会自动升级为高危。
- **社工「高危即时分流」工作台**按时间排列待处置个案，处置四步并全程留痕（**时间 + 响应人**）：
  1. **电话核实**：记录来访原因、量表名称/分值（如 PHQ-9=18）、风险等级，首次保存写入社工响应时间；
  2. **联系紧急联系人**：是否联系上、响应/到场情况**自动写入危机事件记录**（危机事件在居民提交时已由系统自动开立）；
  3. **转介医院**：在“尚未生成预约”阶段直接开转介单，管理者登记回执后分诊闭环；
  4. **风险可控→转入社区咨询**：自动匹配具危机干预资质的咨询师生成预约。
- **咨询师接单前风险画像**：个案详情顶部展示社工核实的来访原因、量表结果、紧急联系人及响应、响应社工与响应时间、全部分诊服务链事件；无危机资质咨询师无法查看/承接。
- 表单显式选择“紧急/危机”等级但**无关键词**的申请，仍走原有“危机资质匹配 + 咨询前初筛”通道，两条通道在数据与看板上互不混淆。
- **状态机（409 防并发覆盖）**：`verify / emergency-contact / refer / admit-community` 仅在 `in_progress` 下合法；重复转介、`admitted_community` 后再转院、`referred/closed`（医院回执后）再转社区接单等冲突操作一律返回 **409 Conflict**，保证医院回执的转介结果不可被社区接单覆盖。
- **时间一致性**：结构化字段统一存 `timestamptz`（UTC）；服务链正文时间一律按显式 **Asia/Shanghai (UTC+8)** 格式化（标注 `(UTC+8)`），前端所有时间（表格字段 + 时间线 + 分诊详情）用同一 +8 规则渲染，容器 `TZ=Asia/Shanghai`，杜绝正文与页面相差 8 小时。
- 管理者看板「高危预约即时分流」卡片统计：触发总数、处置中、已转介医院（含已回执）、转入社区咨询、回执闭环；有未处置个案时生成 critical 级供给建议。

## 五、分权与隐私模型（核心业务规则）

- **认证授权**：JWT + 基于角色的访问控制（居民 / 社工 / 咨询师 / 管理者）。
- **预约与筛查**：居民只能操作本人申请与档案；社工可做咨询前初筛、随访、爽约与危机登记；初筛三结论＝适合社区咨询 / 需家属参与 / 直接转介医院。
- **咨询记录按字段分权**：`咨询过程内容`、`干预建议` 仅**承接该个案的咨询师**可见全文；`风险评估` 对社工可见以保障安全；`下次计划/主题` 对本人（居民）可见；管理者不直接浏览咨询原文。
- **家属查看记录**：默认禁止，必须居民/相关方发起申请 → 管理者审批 → 批准后仅 **72 小时一次性**查看**脱敏风险摘要**（不含咨询过程原文），全程记入服务链。
- **危机与普通咨询分流**：申请阶段按紧急程度/自伤风险自动 `crisisFlag`；匹配时危机单**强制**派给具危机干预资质的咨询师；咨询/随访中风险升级自动开立危机事件；危机处置台与普通预约列表分离展示。
- **一条服务链**：申请、匹配、初筛、记录、爽约、风险升级、危机事件、转介、医院回执、随访、评价、家属申请/审批、请假改约全部写入同一时间线（`service_chain_events`），任一角色在个案详情中按权限查看。

## 六、供给评估（管理者看板）

汇总咨询服务量（近 6 个月）、风险等级分布、初筛决定分布、转介结果分布、危机事件存量、咨询师人均负载与危机承接量，并由规则引擎输出建议：

- 未匹配申请积压 / 人均负载过高 → **建议增加咨询师或排班**；
- 危机占比高而资质人员不足 → **建议社工危机识别培训、扩充危机干预资质**；
- 转介率高或出现医院退回 → **建议深化与精神卫生中心的绿色通道/会诊合作并复盘转介标准**；
- 爽约偏高 → **建议强化提醒与风险个案优先随访**。

转介回执结果回流统计，直接影响上述供给判断（“转介结果会影响社区服务供给”）。

```
/workspace
├── docker-compose.yml        # db + app + web（仅 web 发布宿主端口）
├── .env.example
├── backend/                  # NestJS + TypeORM

│       ├── entities.ts       # 全部领域实体
│       ├── auth.guard.ts / auth.module.ts
│       ├── resident.module.ts    # 预约申请 + 关键词即时分流 + 居民档案/评价/家属申请
│       ├── worker.module.ts      # 高危分流工作台 + 初筛 + 随访 + 爽约 + 危机处置
│       ├── counselor.module.ts   # 排班 + 咨询记录 + 转介 + 请假
│       ├── admin.module.ts       # 看板/供给建议 + 审批 + 转介回执
│       ├── triage.util.ts        # 自伤风险关键词识别
│       ├── match.service.ts      # 资质/时段/主题/危机等级匹配
│       ├── chain.service.ts      # 服务链时间线
│       └── seed.service.ts       # 演示数据
└── frontend/                 # React + Vite + Ant Design
    ├── Dockerfile            # 多阶段、nginx-unprivileged(非 root)、HEALTHCHECK
    ├── nginx.conf            # SPA + /api 反代 app:3000
    └── src/pages/            # Resident / Worker / Counselor / Admin 四套工作台
```

## 八、本地开发（可选，非部署必需）

- 后端：`cd backend && npm install && npm run dev`（需可访问的 PostgreSQL，用 `DB_HOST/DB_USER/...` 环境变量指定）。
- 前端：`cd frontend && npm install && npm run dev`，开发服务器 8080 端口；生产路径下由 nginx 反代 `/api`。
